# ADR-001：本地开发与GPU服务器部署方案

## 状态

已接受

## 日期

2026-08-04

## 问题

OpsPilot应该全部在GPU服务器开发，还是在本地IDE开发后部署到GPU服务器？

## 背景与约束

- 本地Windows环境更适合使用IDE编写和调试代码；
- 本地可能没有足够GPU资源运行Embedding、Reranker和生成模型；
- GPU服务器预计使用Linux，与本地存在路径和依赖差异；
- GPU资源应优先用于推理、评测和性能实验；
- 项目需要可复现、可审查的代码和实验版本；
- 密钥、模型权重、缓存和索引数据不应通过Git同步。

## 候选方案

### 方案一：全部在本地开发和运行

优点：环境简单，调试方便。  
缺点：可能缺少GPU资源，无法完成本地模型和性能实验。

### 方案二：全部通过SSH在GPU服务器开发

优点：开发环境与运行环境一致。  
缺点：依赖网络，长期占用服务器，误操作风险更高。

### 方案三：本地开发，通过Git同步，在GPU服务器运行重型任务

优点：兼顾本地开发效率、GPU资源和版本管理。  
缺点：需要管理Windows与Linux的环境差异。

## 决策

采用方案三：

- 本地完成需求、代码编写、单元测试、API和小样本调试；
- Linux GPU服务器完成Embedding、Reranker、本地大模型推理和压测；
- 使用Git同步代码，不手工维护多份项目副本；
- 后续通过Docker Compose统一API、Qdrant等核心服务；
- 真实`.env`、模型权重、缓存、日志和向量数据不进入Git；
- 使用跨平台路径，不在业务代码中硬编码Windows盘符。

## 选择理由

- 本地IDE开发效率较高；
- 不需要为普通编码和文档工作占用GPU；
- Git可以追踪每次实验对应的代码版本；
- Docker和依赖配置能够减少环境漂移；
- 该模式接近实际团队中的开发与部署流程。

## 风险

1. Windows本地测试通过，但Linux服务器失败；
2. Python、驱动、CUDA、PyTorch或vLLM版本不兼容；
3. 环境变量在服务器遗漏；
4. 代码版本与索引、模型或实验结果不对应；
5. 手工修改服务器代码导致Git状态混乱。

## 缓解措施

- 基础Python版本统一为3.11；
- 路径使用`pathlib`等跨平台方式处理；
- 使用`pyproject.toml`管理基础依赖；
- GPU依赖单独记录并固定实际验证版本；
- 使用`.env.example`说明配置，不提交真实`.env`；
- 记录数据、Prompt、Embedding模型、生成模型和索引版本；
- 服务器改动也必须进入Git提交，避免只存在于服务器；
- 第15天从干净环境验证Docker部署。

## 验证方式

- 本地可以创建虚拟环境并安装开发依赖；
- 本地可以运行Ruff和pytest；
- GPU服务器能够从GitHub拉取项目；
- 服务器能够记录Python、GPU驱动和运行框架版本；
- 相同评测配置能够与Git提交哈希关联；
- 容器重启后索引和必要数据仍然存在。

## 回滚或替代方案

若本地与Linux环境差异导致大量问题，可通过VS Code Remote SSH直接在服务器容器中开发；代码仍然必须通过Git管理，且不改变密钥和数据的隔离原则。

## 后续复审

第15天完成Docker部署后复审本决策；第16天接入本地模型后补充实际Python、驱动、CUDA、推理框架、模型和显存信息。
