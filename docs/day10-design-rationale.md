# Day 10：引用校验、拒答与追问

## 1. 今天解决什么问题

前九天解决了“找哪些文档、怎样排序”。但检索到内容不等于系统应该回答：

- 用户可能只说“报错了怎么办”，缺少版本、日志和命令；
- Top-k 总会返回若干文档，但它们可能只是看起来相似；
- LLM 可能引用不存在的来源，或一句话包含多个没有证据的结论。

Day 10 在检索和生成之间加入安全门，并在生成后加入引用校验。目标不是让
模型“什么都答”，而是让系统知道何时回答、追问或拒答。

## 2. 整体架构与输入输出

~~~mermaid
flowchart LR
    Q["用户问题"] --> R["Hybrid + Reranker 候选"]
    R --> G{"回答安全门"}
    G -->|证据充分| L["LLM 生成带引用结论"]
    G -->|问题含糊| C["生成澄清问题"]
    G -->|证据不足| F["拒答"]
    L --> V{"句子级引用校验"}
    V -->|通过| A["返回答案、引用和原文"]
    V -->|失败| D["降级/重新生成"]
~~~

每一步的数据契约：

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 检索 | question | Dense、BM25、RRF、Reranker | evidence 列表及 score |
| 安全门 | question + evidence | 含糊规则、证据数、分数阈值 | answer/clarify/refuse |
| 生成 | 问题 + 编号证据 | 只能基于证据写结论 | 带 [S1] 的答案 |
| 引用校验 | answer + sources | 检查每个事实句和来源 ID | valid、未知引用、漏引句 |

## 3. 新增文件及作用

- generation/grounding.py：回答决策、澄清问题、拒答响应和句子级引用校验。
- data/eval/day10_grounding_cases.jsonl：18 条受控校准题。
- scripts/evaluate_day10_grounding.py：比较“有结果就回答”和安全策略。
- tests/test_grounding.py：覆盖回答、追问、拒答、漏引和虚假引用。
- data/eval/day10_grounding_results.json：本次实验的完整逐题结果。

## 4. 核心概念

### 4.1 句子级/结论级引用

文档级引用只说明“答案可能来自这篇文档”；句子级引用要求每个可验证结论
紧跟来源，例如：

~~~text
先运行 docker ps -a 查看退出状态。[S1]
再运行 docker logs 查看退出前日志。[S1]
~~~

这样用户能判断是哪条证据支持哪条建议。代码识别 [S数字]，确认 ID 存在，
并检查每个事实句是否带引用。

这只是“结构校验”，不等于“语义支持”。即使 [S1] 存在，模型也可能曲解
原文。更强方案是用 NLI、Cross-Encoder 或人工抽检判断“证据是否蕴含结论”。
本项目先选择结构校验，因为它确定、快速、无需 GPU，适合服务的第一层防线。

### 4.2 可回答性不是模型置信度

LLM 输出概率高，不代表事实正确。可回答性应结合：

1. 问题是否具体；
2. 是否检索到证据；
3. 检索/Reranker 分数是否达到经过校准的阈值；
4. 证据是否覆盖答案的关键结论。

AnswerabilityPolicy 返回三个动作，而不是简单的 True/False：

- answer：证据充分，可以进入生成；
- clarify：领域可能正确，但输入缺关键条件；
- refuse：知识库没有足够证据，继续生成风险高。

### 4.3 阈值与风险权衡

min_top_score=0.35 只是本次受控集上的演示阈值。不同分数不能直接混用：

- 余弦相似度通常有有限范围；
- BM25 分数随语料和查询长度变化；
- Cross-Encoder logit 可能为负数且不等于概率。

生产中应只在 development 调规则、validation 选阈值，test 最后报告一次。
阈值升高通常减少错误回答，但也会增加拒答；阈值降低提高覆盖率，也会增加
无依据回答。医疗、生产删库等高风险场景应更保守，普通文档导航可以更宽松。

## 5. 代码怎样工作

### 步骤 1：检索前不做结论

安全门只接收问题和证据元数据，不自己回答。把策略和 LLM 分开有两个好处：
规则能单测；切换 OpenAI-compatible、vLLM 或本地模型时行为仍一致。

### 步骤 2：先判断是否需要追问

短问题和“怎么办、帮我看看”等含糊表达即使有高分文档也先追问。追问函数
检查版本、错误日志和运行命令是否出现，生成确定性的补充信息清单。这里不用
第二个 LLM，原因是更快、更便宜、不会把用户没有说过的条件编出来。

### 步骤 3：再判断证据是否充分

没有证据或最高分低于阈值时拒答。代码同时返回 reason、top_score 和
evidence_count，便于日志分析“为什么拒答”，而不是只返回一句泛化提示。

### 步骤 4：生成后校验引用

正则先找到答案中的 S1、S2，再与 sources 中允许的 ID 比较；随后按中英文
句末符号切句，找出没有引用的事实句。实现特别处理了“结论。[S1]”这种常见
格式，使引用归属于前面的句子。

## 7. 实验结果与分析

受控集包含 18 题：8 个 answer、5 个 clarify、5 个 refuse。

| 方法 | 动作准确率 | 危险回答率 | 可回答题覆盖率 |
|---|---:|---:|---:|
| Naive：有检索结果就回答 | 50.00% | 90.00% | 100.00% |
| Guarded：含糊规则 + 0.35 阈值 | 100.00% | 0.00% | 100.00% |

这里“危险回答率”指本应追问或拒答的题中仍然选择 answer 的比例。Naive
保住了覆盖率，却对 10 个风险题中的 9 个继续回答。安全门在这个受控集上
没有牺牲可回答题覆盖率。

不能把 100% 当成生产效果。该集合规模小、分数由受控案例提供，主要验证
决策逻辑和指标定义。下一步要在真实 Hybrid/Reranker 分数及脱敏线上请求上
重新校准。Day 9 的 bge-reranker-v2-m3 将 MRR@5 从 0.1754 提高到 0.3591，
说明排序改善明显；但候选 Recall@20 未扩大，因此安全门不能弥补“正确证据
根本没进入候选集”的问题。

## 8. 可替代方案及为何暂不采用

| 方案 | 优点 | 缺点 | 当前选择 |
|---|---|---|---|
| 固定规则和阈值 | 快、透明、可测试 | 跨领域需重新校准 | 采用，作为第一层 |
| LLM 自评“我能否回答” | 能理解复杂语言 | 会过度自信、成本和延迟增加 | 不作为唯一门控 |
| NLI/事实核验模型 | 能检查证据是否蕴含结论 | 多一次模型推理，需训练/校准 | 后续增强 |
| 人工审核 | 高风险场景可靠 | 吞吐低、成本高 | 生产危险操作可加入 |

## 9. 部署思考：宁可拒答还是可能答错

答案取决于错误成本。查看文档链接时，偶尔排序不佳可以允许；执行删除数据、
修改驱动、生产扩缩容时，错误建议的损失远高于一次追问，应提高阈值并要求
多来源一致。建议按请求风险分层：

- normal：一个强证据即可回答；
- elevated：至少两个来源或一个官方直接证据；
- critical：只给检查步骤，不自动执行变更，并要求人工确认。

线上还要持续记录拒答率、追问后解决率、错误反馈率。拒答率过高不是简单下调
阈值的理由，也可能说明知识库缺文档、切块不合理或用户请求分布已经变化。
