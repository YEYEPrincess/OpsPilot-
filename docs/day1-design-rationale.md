# 第1天设计说明：为什么这样定义OpsPilot

本文解释第1天第2～10步的设计原因。重点不是记住文件内容，而是理解每个选择解决了什么问题，以及后续如何验证。

## 1. 第2步：为什么先定义输入、输出和边界

输入输出是系统合同。后续API、Prompt、评测集、日志和前端都必须服从这份合同。若不先定义，项目容易变成输入无限、输出随意、无法验收的聊天Demo。

### 1.1 输入字段为什么这样设计

| 字段 | 设计原因 |
|---|---|
| `query` | 唯一必填字段，表达用户要解决的问题。限制长度可避免空请求、异常Prompt和无意义Token成本。 |
| `error_logs` | 错误码适合BM25精确匹配，日志也需要独立限长和脱敏，因此不与普通问题混成一个字段。 |
| `environment` | 部署故障高度依赖OS、GPU、驱动、CUDA、Python和框架版本。结构化对象便于校验、检索过滤和后续统计。 |
| `component` | 可提示系统优先搜索Docker、CUDA或vLLM文档，但不能作为唯一条件，否则用户标签选错会漏召回。 |
| `conversation_id` | 允许关联有限追问；不默认保存无限历史，避免成本增加和旧信息污染当前诊断。 |

为什么不使用一个大字符串：单字符串虽然实现简单，但无法分别校验问题和日志，难以脱敏、统计和生成稳定API文档，长日志也容易淹没真正的问题。

### 1.2 输出字段为什么这样设计

结构化输出同时服务用户界面、评测系统和运行日志。自由文本无法稳定区分原因、排查、修复、风险和引用。

| 字段 | 设计原因 |
|---|---|
| `request_id` | 将用户请求、后端日志、错误和反馈关联起来，便于线上排障。 |
| `summary` | 先给用户一个简短方向，但不能把猜测写成确定根因。 |
| `possible_causes` | 真实故障通常有多个候选原因；保留优先级和引用比强选一个原因更可靠。 |
| `diagnostic_steps` | 强制按顺序先验证、后修改，并给每步标记风险。 |
| `suggested_fixes` | 排查与修复分开，避免原因尚未确认就直接修改生产环境。 |
| `risk_notes` | 让前端突出重启、删除、覆盖和权限修改等风险。 |
| `citations` | 体现RAG的证据价值。URL由检索元数据提供，不能由模型自由编造。 |
| `answerable` | 判断现有知识与信息是否足以作答，而不是判断语言是否流畅。 |
| `confidence` | 表示证据强度；首版是可解释等级，不是假装精确的概率。 |
| `clarifying_questions` | 信息不足时告诉用户需要补充版本、日志或资源数据，使拒答仍能推动排障。 |
| `latency_ms` | 拆分检索、重排、生成和总延迟，才能定位真正的性能瓶颈。 |

### 1.3 为什么必须定义不可回答场景

知识库一定存在覆盖边界。没有拒答设计，系统会把信息不足误装成“模型知道答案”。以下情况应拒答或追问：

- 没有相关证据或引用不能支持结论；
- 缺少必要版本、环境和日志；
- 用户询问没有文档的私有系统；
- 问题超出大模型部署领域；
- 用户要求执行高风险操作；
- 多种原因无法由现有信息区分。

拒答不是模型能力弱，而是可靠诊断系统的必要行为。

## 2. 第3步：验收指标为什么这样设计

指标分为检索、生成、安全、服务和工程五层。只评价最终回答会掩盖错误来源：回答错可能是没召回证据，也可能是证据正确但模型没有利用。

| 指标 | 目标 | 选择原因 |
|---|---:|---|
| Recall@5 | ≥0.85 | 第一阶段检索负责尽量不漏证据，后面还有Reranker，所以看前5而非只看第1。0.85对20天小型知识库有挑战但可实现。 |
| MRR@10 | ≥0.70 | Recall只看有没有，MRR还看正确证据排得多靠前，用来验证融合和重排价值。 |
| 人工正确性 | ≥4/5 | 部署答案包含正确性、完整性和可执行性，不能只靠字符串匹配。4分代表总体正确且没有关键错误。 |
| 引用支持率 | ≥0.90 | 不是检查“有没有链接”，而是检查引用是否真正支持对应结论。诊断场景风险较高，因此目标较严格。 |
| 拒答准确率 | ≥0.80 | 在幻觉风险和过度拒答之间建立首版基线；还要分别统计错误回答和错误拒答。 |
| 测试API成功率 | ≥99% | 只针对可控测试环境，不是假装承诺生产SLA，用于验证预期异常不会让服务崩溃。 |
| 云端模型P95 | ≤8秒 | P95比平均值更能暴露慢请求；诊断类应用可以容忍一定思考时间，但还要单独测首Token延迟。 |
| 核心测试覆盖率 | ≥60% | 推动检索融合、Schema、拒答和指标计算可验证，又不为追求数字测试无价值展示代码。 |

这些数字当前是“验收目标”，不是项目成果。只有使用冻结评测集实测后，真实结果才能写进简历。

## 3. 第4步：20个种子问题是怎么提出的

不是随机想20句话，而是使用“故障分类×问题形式×可回答性”设计覆盖矩阵。

### 3.1 故障分类

- Docker：启动、端口、挂载和持久化；
- GPU/CUDA：容器可见性、驱动与PyTorch兼容；
- vLLM/模型：OOM、首Token、并发、上下文和下载；
- Linux/存储：权限与磁盘；
- FastAPI/Qdrant：并发和容器网络；
- RAG：分块与Embedding；
- 负样本：信息不足、高风险和领域外问题。

### 3.2 问题形式

- 现象型：服务启动后立即退出；
- 错误码型：`CUDA driver version is insufficient`；
- 原理型：上下文长度为什么增加显存；
- 排查型：应检查哪些环节；
- 性能型：并发增加后为什么超时；
- 安全型：要求删除所有缓存；
- 越界型：询问天气。

不同形式用于检验不同能力：错误码有利于BM25，语义描述有利于向量检索，复杂排查可能需要多个证据片段。

### 3.3 为什么加入3个不可回答问题

如果评测集全部可回答，模型永远不拒答也能得高分。信息不足、高风险和领域外问题用于从第一天验证拒答边界。

当前只叫“种子问题”，因为还没有标准文档、标准Chunk、参考要点和难度。第6天会扩展成50～100题正式评测集，并补充：

```json
{
  "gold_document_ids": ["docker-doc-001"],
  "gold_chunk_ids": ["docker-doc-001#chunk-12"],
  "reference_points": ["检查退出码", "查看容器日志"],
  "difficulty": "easy",
  "split": "test"
}
```

## 4. 第5步：目录结构为什么这样划分

目录按职责而不是开发日期划分：

| 目录 | 职责 |
|---|---|
| `app/` | API路由及请求响应模型 |
| `core/` | 配置、日志、异常和公共能力 |
| `ingestion/` | 文档解析、清洗、分块和建库 |
| `retrieval/` | BM25、向量检索、融合和Reranker |
| `generation/` | Prompt、LLM客户端、引用和拒答 |
| `evaluation/` | 离线指标和实验脚本 |
| `frontend/` | 演示界面 |
| `tests/` | 自动化测试 |
| `configs/` | 可版本化实验配置 |
| `scripts/` | 建库、评测和压测入口 |
| `data/` | 原始、处理后和评测数据 |
| `docs/` | 需求、ADR、架构与实验报告 |

这样能把数据处理、在线查询、答案生成和离线评测分开。后续替换向量库或模型时，不必修改整个应用。`.gitkeep`用于让Git保留空目录。

## 5. 第6步：为什么选择Python 3.11和`.venv`

Python 3.11兼顾现代语言特性、性能和AI生态兼容性。项目允许`>=3.11,<3.13`，暂时避免过旧解释器，也避免部分GPU依赖尚未适配更新版本。

`.venv`将项目依赖与系统Python、其他项目隔离。升级某个库不会破坏其他项目；删除`.venv`也可以安全重建。

本项目使用：

- `.python-version`：声明3.11系列；
- `pyproject.toml`：声明允许的依赖范围；
- `uv.lock`：锁定本次解析到的精确版本；
- `.venv`：实际隔离环境，不进入Git。

推荐命令：

```powershell
uv sync --extra dev
uv run python --version
uv run ruff check .
uv run pytest
```

## 6. 第7步：`pyproject.toml`是干什么的

它是Python项目的标准配置入口，集中描述：

- `[build-system]`：使用Hatchling构建项目；
- `[project]`：名称、版本、Python范围和运行依赖；
- `optional-dependencies.dev`：pytest、覆盖率和Ruff等开发依赖；
- pytest和Ruff的统一规则。

运行依赖是服务启动需要的库；开发依赖只用于测试和检查，生产镜像可以不安装，减小体积和攻击面。

依赖没有在`pyproject.toml`里完全钉死，因为它表达人的兼容范围，例如`fastapi>=0.115,<1.0`；`uv.lock`负责记录机器实际安装的精确版本。前者表达设计意图，后者保证复现。

## 7. 第7步：`.env.example`是干什么的

它是“环境变量说明模板”，告诉开发者运行系统需要哪些配置，但不能包含真实密钥。使用方式：

```powershell
Copy-Item .env.example .env
```

真实值只写入本地`.env`，`.gitignore`会忽略它。

- `APP_*`控制应用运行；
- `LLM_*`控制生成模型；
- Embedding和Reranker变量控制检索模型；
- `QDRANT_*`控制向量数据库；
- `TOP_K_*`与超时属于可实验的运行参数。

这些参数不能硬编码，因为本地、GPU服务器和Docker使用的地址、模型和密钥不同。即使仓库当前私有，也不能提交密钥，因为Git历史可能长期保留它。

## 8. 第8步：为什么第一天就写README

README是项目入口，不是最后补的宣传材料。它应从第一天回答：项目解决什么问题、面向谁、范围是什么、如何安装、当前完成了什么、安全边界是什么。持续更新README能检验项目是否真正可复现，也自然形成GitHub作品集。

## 9. 第9步：为什么需要ADR

ADR是架构决策记录。代码说明“做了什么”，ADR说明“为什么这样做”。第一份ADR记录本地开发、Git同步和GPU服务器运行的候选方案、约束、风险、缓解与复审时间。

ADR不是证明选择永远正确，而是让选择在当时约束下可解释、可验证、可回滚。

## 10. 第10步：为什么尽早使用Git

Git用于记录每次功能和实验对应的代码、在本地与GPU服务器之间同步、发现意外修改并展示持续开发过程。

建议每项独立变化单独提交：

```text
feat(ingestion): add HTML document parser
feat(retrieval): implement BM25 baseline
test(evaluation): add recall and MRR metrics
docs: record chunk-size experiment
```

提交前检查：

1. 是否包含`.env`或密钥；
2. 是否包含模型权重、缓存或大数据；
3. 测试和静态检查是否通过；
4. 提交信息是否说明了变化目的。

## 11. 如何判断第1天设计有效

- 任意功能都能判断是否属于首版范围；
- 每个输出字段都有明确消费者；
- 每个指标都能通过脚本或评分规则测量；
- 种子问题能够指导第2天收集文档；
- 本地和GPU服务器可以依据配置重建；
- 新开发者可通过README理解项目；
- 技术选择可通过ADR解释和复审。

如果后续实验推翻当前假设，应更新需求或ADR并记录原因。工程设计的价值在于可验证和可修正，不在于第一天就永远正确。
