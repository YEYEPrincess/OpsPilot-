# 第2天：知识库数据收集与治理说明

> 数据集版本：`source-catalog-v0.1.0`  
> 采集范围：大模型应用部署与RAG基础设施官方文档  
> 原始快照策略：仅本地保存，不提交GitHub

## 1. 今天的数据目标

首版选取44个官方文档页面，覆盖：

- Docker容器、日志、网络、资源和持久化；
- NVIDIA Container Toolkit安装、验证和排障；
- PyTorch CUDA、安装、序列化和可复现性；
- vLLM安装、服务、显存、量化、分布式和故障排查；
- FastAPI部署、Worker、Docker、异步和异常；
- Qdrant集合、存储、索引和部署；
- Kubernetes Pod、资源、探针、存储、镜像和调试。

44页足以支持首版种子问题，又没有扩大到难以治理的整站规模。第6天评测若发现明显知识缺口，再根据失败案例定向增加页面。

## 2. 为什么优先选择官方文档

### 当前选择

使用产品官方文档作为第一层可信来源。

### 可替代方案

1. 技术博客；
2. Stack Overflow和论坛；
3. GitHub Issues；
4. 搜索引擎实时搜索；
5. 企业内部故障单。

### 为什么首版不选替代方案作为主体

- 博客和论坛可能过时、缺少版本说明或包含未经验证的做法；
- GitHub Issue很有价值，但讨论可能包含猜测和未合并方案；
- 实时搜索难以保证每次实验使用相同证据；
- 企业故障单更真实，但可能包含隐私、主机名、IP、账号和密钥；
- 官方文档许可和来源更容易追踪。

社区案例适合在首版基线稳定后作为第二层证据，并应与官方证据区分权重。

## 3. 为什么选择精选页面而不是整站爬取

### 当前选择

维护人工审核的`source_catalog.csv`，只采集与种子问题直接相关的页面。

### 替代方案A：抓取整个网站

优点是覆盖大。缺点是会混入导航页、营销页、多语言重复页、旧版本和大量无关内容，还会增加站点负载和治理成本。

### 替代方案B：克隆全部文档Git仓库

优点是版本精确、Markdown通常更干净。缺点是每个项目仓库结构不同，可能包含网站源码、图片、翻译、历史内容和构建依赖，许可边界也不一定等同于渲染网站的所有素材。

### 不选择替代方案的原因

当前目标是20天内完成高质量闭环，而不是构建通用爬虫。精选页面让每个来源都可以回答“为什么进入知识库”，并便于定位缺失和过期内容。

## 4. 为什么保存HTML快照而不只保存URL

只保存URL最省空间，但网页会更新、重定向或消失，后续实验无法复现。保存采集时的HTML可以保证：

- 同一数据版本能够重新解析；
- Chunk和索引问题可追溯到原始页面；
- 页面更新前后可以通过哈希比较；
- 网络不可用时仍可开发解析流程。

### 为什么不提交HTML到GitHub

- 原始网页可能包含图片、商标、脚本或第三方内容；
- 仓库许可不一定覆盖渲染网页中的全部资源；
- 快照会增加仓库体积；
- 页面可通过脚本和公开URL重新下载。

因此Git只保存清单、采集脚本、报告和哈希；HTML保存在被`.gitignore`排除的`data/raw/`中。

## 5. 为什么使用CSV清单

CSV便于人工审核、Git Diff和电子表格查看，也可以由Python标准库直接读取。

替代方案包括JSONL、YAML和数据库：

- JSONL适合嵌套字段，但人工横向检查不如CSV；
- YAML可读性好，但需要额外解析依赖，缩进错误也较常见；
- SQLite适合大量数据查询，但当前44条记录不值得增加二进制文件和迁移成本。

后续元数据变复杂时，可以将CSV升级为JSONL或数据库；目前CSV是最小且透明的选择。

## 6. 元数据字段设计

### 人工维护字段

| 字段 | 用途 |
|---|---|
| `document_id` | 稳定唯一标识，URL变化时仍可关联实验 |
| `product` | 产品过滤和统计 |
| `topic` | 主题过滤和覆盖分析 |
| `title` | 人工预期标题，帮助发现错误重定向 |
| `source_url` | 原始来源 |
| `source_kind` | 官方文档、博客或Issue等来源级别 |
| `language` | 后续选择分词和Embedding策略 |
| `license_id` | SPDX标识或`REVIEW_REQUIRED` |
| `license_evidence_url` | 许可证据位置 |
| `redistribution_status` | 是否允许提交原文；当前统一仅本地快照 |
| `enabled` | 无需删除记录即可停用来源 |

### 采集生成字段

| 字段 | 用途 |
|---|---|
| `final_url` | 记录重定向后的真实地址 |
| `http_status` | 检查缺失和访问错误 |
| `retrieved_at` | 记录数据版本时间 |
| `bytes` | 发现空页面和异常大页面 |
| `sha256` | 原始字节精确去重和完整性检查 |
| `text_sha256` | 忽略脚本、样式和空白后的文本去重 |
| `encoding` | 解析时选择正确字符集 |
| `replacement_char_count` | 发现解码损坏 |
| `detected_title` | 检查页面是否抓到了预期内容 |
| `suspected_secret_pattern_count` | 标记疑似密钥，报告数量但不打印秘密 |
| `error` | 记录失败原因，不让单页失败终止全任务 |

## 7. 重复、缺失和编码检查

### 7.1 重复检查

采用两层哈希：

1. `sha256`：原始文件完全相同；
2. `text_sha256`：去掉脚本、样式并规范空白后的正文相同。

替代方法是Embedding相似度去重，它能发现语义近似页面，但成本更高且阈值主观。第2天先做确定性去重；第3天完成文本解析后再考虑近重复检测。

### 7.2 缺失检查

以下情况标记失败：

- 网络或超时错误；
- HTTP状态不是200；
- 内容小于500字节；
- 无法写入本地快照。

脚本允许单页失败后继续运行，因为批量数据任务不应因一个来源临时不可用而全部丢失。

### 7.3 编码检查

优先采用HTTP响应声明的编码，失败时回退UTF-8并统计Unicode替换字符`�`。替换字符大于0时必须人工抽查。

替代方案是安装字符集自动检测库。首版页面均来自现代官方站点，通常是UTF-8，因此暂不增加依赖；若后续引入旧PDF或中文论坛，再加入自动检测。

## 8. 许可证治理

当前清单记录的是上游项目或文档仓库的许可证证据，不将它自动解释为对网站全部素材的法律结论。

| 来源 | 记录的许可证 | 处理方式 |
|---|---|---|
| Docker Docs | `REVIEW_REQUIRED` | 只保留本地快照，不再分发 |
| NVIDIA Container Toolkit | Apache-2.0 | 仍只保留本地快照 |
| PyTorch Docs | BSD-3-Clause | 保留来源和版权信息 |
| vLLM | Apache-2.0 | 保留来源和许可证据 |
| FastAPI | MIT | 保留来源和许可证据 |
| Qdrant Docs | Apache-2.0 | 保留来源和许可证据 |
| Kubernetes Docs | CC-BY-4.0 | 引用时保留署名和来源 |

若将来要公开分发处理后的完整正文，必须重新核对每个来源的许可证、署名要求、第三方素材和商标要求。当前项目不是法律意见。

## 9. 隐私、密钥与日志边界

### 9.1 当前公开文档

官方文档原则上不应包含真实用户隐私，但可能包含示例Token、内部路径或看似密钥的占位符，因此采集后仍执行疑似密钥模式扫描。

### 9.2 未来用户日志

允许进入临时请求上下文：

- 错误类型和错误码；
- 软件版本；
- GPU型号和资源占用；
- 已脱敏的配置片段；
- 必要的堆栈信息。

默认禁止写入长期日志或索引：

- API Key、Cookie、Authorization Header；
- 私钥、密码和数据库连接串；
- 用户姓名、邮箱和访问Token；
- 内部域名、私有IP和主机名，除非经过授权与脱敏；
- 完整环境变量；
- 不必要的完整用户日志。

### 9.3 日志建议

默认记录请求ID、组件、错误类型、各阶段延迟、文档ID、Chunk ID和模型版本，不记录完整问题、完整检索正文或完整生成答案。调试日志若临时包含原文，应设置短保留期和访问控制。

### 9.4 索引建议

索引只保存经批准的知识库正文和必要元数据，不保存用户查询日志。用户反馈与知识索引分开存储，避免把私人故障描述意外变成后续用户可检索的知识。

## 10. 开发、验证和测试数据边界

RAG首版不训练基础模型，因此这里的“开发集”用于调Prompt和检索，“验证集”用于选配置，“测试集”用于最终无偏评测。

- 开发集60%：可反复查看，用于定位错误和开发功能；
- 验证集20%：用于选择Chunk大小、Top-k、融合权重和拒答阈值；
- 测试集20%：优化期间不查看结果，只在里程碑和最终报告运行。

种子问题的临时划分保存在`data/eval/split_policy.json`。

### 为什么文档知识库不按问题划分一并切断

测试问题本来就应当使用知识库中的公开文档作答。如果把相关文档从测试时的索引中删除，测试的将变成“知识缺失时能否猜测”，而不是RAG检索能力。

真正需要隔离的是：

- 不用测试问题反复修改Prompt；
- 不把测试问题原文写入知识库；
- 不根据测试结果选择Top-k和阈值；
- 最终报告必须记录数据、代码、Prompt和索引版本。

替代方案是按文档来源做“未见域测试”，它可以测试跨产品泛化，但不适合作为首版主指标，可在后续增加为挑战集。

## 11. 运行方式

```powershell
Set-Location "D:\Documents\大模型项目\opspilot"
.\.venv\Scripts\python.exe scripts\collect_docs.py
```

输出：

- `data/raw/<product>/`：本地HTML快照，不提交Git；
- `data/manifest/download_report.csv`：逐页采集和质量报告；
- `data/manifest/collection_summary.json`：总体统计。

重新运行会覆盖同一`document_id`的本地快照和报告，从而形成新的数据快照。正式实验时应将清单、报告和Git提交哈希一起记录。
