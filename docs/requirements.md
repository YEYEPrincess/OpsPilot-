# OpsPilot 产品与系统需求说明书

> 项目名称：OpsPilot——面向大模型应用部署的智能故障诊断RAG系统  
> 文档版本：v0.1.0  
> 文档状态：第一阶段基线  
> 项目周期：20天  
> 最后更新：2026-08-03

---

## 1. 文档目的

本文档用于明确OpsPilot首个版本的目标用户、使用场景、输入输出、功能需求、非功能需求、系统边界、验收指标和失败判定标准。

在项目实施过程中，新增功能必须先判断是否属于本文档定义的首版范围。若会明显增加项目周期，应记录为后续版本需求，避免20天项目失控。

---

## 2. 项目背景

大模型和RAG应用在部署过程中经常涉及Docker、Linux、NVIDIA驱动、CUDA、PyTorch、vLLM、FastAPI、Qdrant以及网络、存储和权限配置。故障信息通常分散在官方文档、FAQ和错误日志中，开发者需要跨多个来源搜索、比较并验证解决方案。

通用大语言模型虽然可以直接回答技术问题，但可能存在以下问题：

- 回答缺乏可验证的文档依据；
- 对版本差异和运行环境考虑不足；
- 在信息不足时仍然生成看似合理的结论；
- 无法区分检索失败、知识库缺失和生成错误；
- 缺少面向部署场景的结构化排查流程；
- 无法稳定记录质量、延迟、Token和资源消耗。

OpsPilot通过检索增强生成技术，从可信技术文档中检索证据，再生成带引用、结构化、可追溯的故障诊断建议。当证据或环境信息不足时，系统应明确拒绝判断或向用户提出补充问题。

---

## 3. 项目目标

### 3.1 总体目标

在20天内实现一个可运行、可评测、可部署、可演示的大模型应用部署故障诊断系统，覆盖从文档处理、混合检索、重排序、答案生成、引用校验到API服务、Docker部署和性能评测的完整工程链路。

### 3.2 产品目标

系统应帮助用户：

1. 根据故障描述快速定位可能原因；
2. 按风险和优先级获得排查步骤；
3. 查看每条关键结论的文档来源；
4. 识别还缺少哪些环境信息；
5. 在知识库没有充分证据时避免获得武断答案。

### 3.3 技术目标

项目应实现并验证：

- 多格式技术文档解析和标准化；
- 章节感知或固定长度文本分块；
- BM25关键词检索；
- Embedding向量检索；
- 混合检索结果融合；
- Cross-Encoder或同类Reranker重排序；
- 结构化答案生成；
- 引用溯源和证据不足拒答；
- 离线评测与对照实验；
- FastAPI服务化；
- Docker Compose部署；
- 日志、延迟、错误和资源指标记录。

### 3.4 求职展示目标

最终项目应能够证明开发者具备以下能力：

- 将业务问题转化为可验证的系统需求；
- 独立实现生产级RAG核心链路；
- 使用实验指标定位并优化检索与生成问题；
- 理解本地开发、GPU推理和容器部署的差异；
- 分析质量、延迟、吞吐、显存和成本之间的权衡；
- 编写可复现的部署文档和技术决策记录。

## 4. 目标用户

### 4.1 主要用户

- 初级大模型应用开发工程师；
- RAG应用开发工程师；
- 需要部署本地推理模型的算法工程师；
- 负责AI服务的后端开发人员；
- 初级AI平台或运维工程师。

### 4.2 用户特征

目标用户通常具备基本的Python和Linux知识，但可能：

- 不熟悉GPU容器的完整配置链路；
- 无法快速判断CUDA、驱动和框架之间的兼容关系；
- 不清楚模型加载失败发生在哪一层；
- 面对多个文档来源时难以组织排查顺序；
- 不熟悉服务并发、超时、缓存和持久化问题。

### 4.3 非目标用户

首版不专门面向：

- 完全不具备计算机基础的普通用户；
- 需要系统自动修复生产环境的企业运维团队；
- 需要多租户权限、审计和SLA保障的大型企业客户；
- 需要训练或微调基础大模型的研究人员。

## 5. 使用场景

### 5.1 核心场景

系统首版覆盖以下六类问题：

1. Docker镜像、容器启动、端口、挂载和持久化故障；
2. NVIDIA驱动、GPU识别、CUDA和PyTorch兼容问题；
3. vLLM或其他本地推理服务的模型加载、显存和吞吐问题；
4. FastAPI模型服务的超时、并发和异常问题；
5. Qdrant等RAG基础设施的连接、索引和数据持久化问题；
6. Linux环境中的磁盘、文件权限、网络端口和进程问题。

### 5.2 示例场景

#### 场景A：容器无法使用GPU

用户输入：

> 宿主机运行nvidia-smi正常，但Docker容器中无法识别GPU，应如何排查？

系统应：

- 识别问题属于GPU容器环境；
- 检索NVIDIA容器工具相关文档；
- 列出从宿主机驱动到容器启动参数的排查顺序；
- 给出引用和风险提示；
- 若缺少Docker版本等必要信息，提出补充问题。

#### 场景B：vLLM加载模型时显存不足

用户输入：

> 24GB显卡加载14B模型时出现CUDA out of memory。

系统应：

- 说明可能涉及权重、KV Cache、上下文长度和并发配置；
- 建议用户补充模型精度、量化方式和启动参数；
- 给出由低风险到高影响的排查和调整顺序；
- 不应在缺乏证据时保证某个参数一定能够解决问题。

#### 场景C：知识库没有答案

用户输入：

> 我们公司的内部推理服务昨晚突然崩溃，请直接告诉我根本原因。

系统应：

- 判断现有信息不足；
- 不编造根本原因；
- 请求用户提供错误日志、服务版本、资源使用情况和近期变更；
- 将`answerable`设置为`false`。

## 6. 数据范围

### 6.1 首版知识来源

首版优先使用公开、可信、允许合理使用的技术资料：

- Docker官方文档；
- NVIDIA Container Toolkit官方文档；
- NVIDIA CUDA相关公开文档；
- PyTorch官方文档；
- vLLM官方文档；
- FastAPI官方文档；
- Qdrant官方文档；
- Kubernetes官方故障排查文档；
- 项目允许使用的公开FAQ或故障案例。

### 6.2 文档格式

系统计划支持：

- PDF；
- HTML；
- Markdown；
- TXT。

### 6.3 文档元数据

每份文档至少保存：

| 字段 | 说明 |
|---|---|
| `document_id` | 文档唯一标识 |
| `title` | 文档标题 |
| `source_url` | 原始来源地址 |
| `source_type` | PDF、HTML、Markdown或TXT |
| `product` | Docker、vLLM、PyTorch等产品标签 |
| `version` | 文档对应版本，未知时为空 |
| `section` | 章节路径 |
| `page` | PDF页码，可选 |
| `updated_at` | 来源更新时间，可选 |
| `content_hash` | 内容哈希，用于去重和版本识别 |

### 6.4 数据安全要求

- 首版只使用公开资料或经明确授权的文档；
- 不将API密钥、密码和访问Token写入知识库；
- 不提交包含敏感数据的原始文档；
- 不在普通日志中保存完整用户日志或大段原文；
- 用户输入若包含疑似密钥，应在日志中进行遮蔽。

## 7. 系统输入需求

### 7.1 查询输入

系统查询接口接受以下字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `query` | string | 是 | 用户的故障问题 |
| `error_logs` | string | 否 | 相关错误日志片段 |
| `environment` | object | 否 | 操作系统、GPU、驱动、CUDA等信息 |
| `component` | string | 否 | Docker、CUDA、vLLM等组件标签 |
| `conversation_id` | string | 否 | 有限追问场景的会话标识 |

### 7.2 输入示例

```json
{
  "query": "Docker容器中启动vLLM时出现CUDA out of memory，应如何排查？",
  "error_logs": "torch.OutOfMemoryError: CUDA out of memory",
  "environment": {
    "os": "Ubuntu 22.04",
    "gpu": "NVIDIA RTX 4090 24GB",
    "python": "3.11",
    "model": "14B parameter model"
  },
  "component": "vllm"
}
```

### 7.3 输入校验

- `query`去除首尾空格后不得为空；
- 首版建议将`query`限制在2000字符以内；
- 首版建议将`error_logs`限制在10000字符以内；
- 超长内容必须返回明确的参数错误；
- 输入不得直接拼接到系统命令中；
- 日志内容只作为检索和判断上下文，不允许被自动执行。

- 关键故障结论必须关联至少一个引用；
- 引用必须来自本次实际检索到的文档片段；

- 证据不足时必须返回`answerable=false`；
- 证据不足时优先提出具体、可回答的补充问题。

## 9. 功能需求

需求优先级说明：

- P0：首版必须实现，否则项目不能验收；
- P1：应当实现，可在核心链路完成后加入；
- P2：进阶功能，时间不足时可延期。

### FR-001 文档导入（P0）

系统必须能够从指定目录读取支持的文档，并为每份文档生成唯一标识和元数据。

验收条件：

- 能够导入至少30份技术文档；
- 单份文档失败不会导致整个导入任务退出；
- 导入结果能够记录成功数、失败数和失败原因。

### FR-002 文档清洗与分块（P0）

系统必须能够清理无效内容，并按照可配置策略对文档分块。

验收条件：

- 每个Chunk保留文档、章节和来源信息；
- Chunk大小和重叠长度可以配置；
- 相同内容能够通过哈希识别重复；
- 可以输出Chunk数量、长度分布和失败统计。

### FR-003 向量索引（P0）

系统必须能够为Chunk生成Embedding并写入向量数据库。

验收条件：

- 支持批量生成Embedding；
- 支持重复运行时跳过未变化内容或重建指定版本；
- 向量记录能够关联原始Chunk和元数据；
- 索引版本可以追踪。

### FR-004 BM25关键词检索（P0）

系统必须实现关键词检索，以处理错误码、命令参数和产品名称等精确词汇。

验收条件：

- 输入查询后能够返回Top-k结果；
- 返回结果包含分数、文本和来源；
- k值可以通过配置调整。

### FR-005 向量检索（P0）

系统必须实现语义向量检索。

验收条件：

- 输入中文或英文问题后能够返回Top-k结果；
- 结果包含向量分数和元数据；
- 查询失败时返回可识别的错误类型。

### FR-006 混合检索（P0）

系统必须融合BM25和向量检索结果。

验收条件：

- 至少实现一种融合方法，如RRF；
- 能够分别记录两个检索器的候选结果；
- 能够与纯BM25和纯向量检索进行对照评测。

### FR-007 Reranker重排序（P0）

系统必须对混合检索候选结果进行重排序。

验收条件：

- 重排序输入候选数量和输出数量可配置；
- 能记录重排序耗时；
- 能通过配置关闭Reranker，以便运行对照实验。

### FR-008 结构化答案生成（P0）

系统必须依据检索证据生成结构化诊断答案。

验收条件：

- 返回摘要、可能原因、排查步骤、建议修复和风险提示；
- 输出符合预定Schema；
- 模型返回非法结构时，系统能够有限重试或返回明确错误；
- Prompt版本可以追踪。

### FR-009 引用溯源（P0）

系统必须为关键结论提供引用。

验收条件：

- 引用能够定位到文档标题和章节；
- 引用URL来自知识库元数据，不由模型自由生成；
- 引用原文必须属于本次检索上下文；
- 用户可以查看引用原文片段。

### FR-010 可回答性判断与拒答（P0）

系统必须判断现有证据是否足以支持回答。

验收条件：

- 对知识库外问题返回`answerable=false`；
- 对信息不足问题提出补充问题；
- 不可回答时不得生成确定性的根本原因；
- 可回答性阈值或规则可以配置和评测。

### FR-011 FastAPI服务（P0）

系统必须提供HTTP API。

首版至少包含：

- `POST /api/v1/query`：提交诊断问题；
- `GET /api/v1/health/live`：进程存活检查；
- `GET /api/v1/health/ready`：依赖与模型就绪检查；
- `GET /api/v1/version`：返回应用、Prompt和索引版本。

验收条件：

- 请求和响应具有Pydantic校验；
- 每个请求返回或记录`request_id`；
- 参数错误、依赖错误、超时和内部错误能够区分；
- API自动文档可以访问。

### FR-012 Web演示界面（P1）

系统应提供简单Web界面。

验收条件：

- 用户可以输入问题和错误日志；
- 页面显示生成过程或流式文本；
- 页面展示结构化答案和引用；
- 用户可以提交有帮助/无帮助反馈。

### FR-013 结构化日志（P0）

系统必须记录核心运行信息。

日志至少包括：

- 请求ID；
- 时间戳；
- 请求状态；
- 检索、重排序、生成和总耗时；
- 候选数量；
- 使用的模型、Prompt和索引版本；
- Token用量；
- 缓存是否命中；
- 错误类型。

日志不得默认保存真实密钥或完整敏感内容。

### FR-014 配置管理（P0）

系统必须通过环境变量和配置文件管理运行参数。

验收条件：

- 仓库包含`.env.example`；
- 真实`.env`不进入Git；
- 模型地址、模型名称、Top-k、超时和索引名称可以配置；
- 缺少必要配置时，应用启动应给出明确错误。

### FR-015 Docker部署（P0）

系统必须支持Docker Compose部署。

验收条件：

- 至少编排API和Qdrant；
- 数据使用持久化卷；
- 容器包含健康检查；
- 密钥不写入镜像；
- 第三方可以按照README从空环境启动服务。

### FR-016 缓存（P1）

系统应支持对安全且适合复用的结果进行缓存。

验收条件：

- 缓存键包含影响答案的模型、Prompt和索引版本；
- 缓存具有TTL；
- 缓存命中能够被记录；
- 索引更新后不会长期返回过期结果。

### FR-017 用户反馈（P1）

系统应记录用户对回答的简单评价。

验收条件：

- 支持有帮助/无帮助；
- 反馈与请求ID关联；
- 不要求用户提交敏感信息；
- 反馈可以导出用于后续错误分析。

### FR-018 本地与云端模型切换（P1）

系统应通过统一接口支持云端API模型和本地推理模型。

验收条件：

- 切换模型不需要修改检索逻辑；
- 模型名称和地址通过配置指定；
- 能分别记录两个方案的质量、延迟、显存和成本。

## 10. 非功能需求

### NFR-001 性能

- 应分别记录检索、重排序、首Token、生成和总延迟；
- 使用云端模型时，目标P95端到端延迟不高于8秒；
- 本地模型延迟根据实际GPU测试，不预设虚假目标；
- 应测量1、2、4、8等不同并发下的吞吐和错误率；
- 长时间请求必须具有可配置超时。

### NFR-002 稳定性

- 单个请求失败不得导致服务进程退出；
- 文档导入任务应允许记录部分失败；
- 外部模型超时应返回明确错误；
- Qdrant不可用时，就绪检查应失败；
- 重试必须限制次数，避免故障放大；
- 测试环境核心API成功率目标不低于99%。

### NFR-003 安全性

- 系统不得自动执行用户输入的命令；
- 删除、覆盖、权限修改等操作必须标记为高风险；
- API密钥通过环境变量注入；
- `.env`、模型缓存和私有数据不得进入Git；
- 日志对疑似密钥进行遮蔽；
- 用户输入不得未经处理直接进入Shell或数据库查询。

### NFR-004 可观测性

- 所有查询具备唯一请求ID；
- 日志能够区分解析、检索、重排序、生成和依赖错误；
- 能够计算P50、P95延迟和错误率；
- 能够观察Token用量和缓存命中率；
- 条件允许时记录CPU、内存、GPU显存和GPU利用率。

### NFR-005 可维护性

- 文档处理、检索、生成、API和评测模块相互分离；
- 核心参数不得散落硬编码；
- 公共接口具有类型标注；
- 核心模块具有单元测试；
- README必须描述本地运行和服务器部署方法。

### NFR-006 可复现性

- 固定Python主版本和依赖范围；
- 保存数据版本、模型版本、Prompt版本和索引版本；
- 每次实验保存配置、时间和结果；
- Docker镜像和Compose配置纳入版本管理；
- 第三方应能够根据README复现基础服务。

### NFR-007 可移植性

- 业务代码不得硬编码Windows盘符；
- 文件路径统一使用跨平台方式处理；
- 本地开发环境可以是Windows；
- GPU推理目标环境为Linux服务器；
- GPU专属依赖与基础应用依赖应合理分离。

## 12. 不可回答与拒答规则

满足以下任一条件时，系统应拒绝确定性回答或提出澄清问题：

1. 检索结果与问题相关性低于可配置阈值；
2. 检索内容无法支持关键结论；
3. 用户询问私有系统，但未提供相关文档或上下文；
4. 用户只说“服务崩了”，没有日志、版本或环境信息；
5. 问题不属于大模型应用部署领域；
6. 用户要求系统直接执行高风险操作；
7. 多种故障原因无法根据当前信息区分；
8. 文档之间存在明显冲突且无法依据版本判断。

拒答示例：

```json
{
  "summary": "现有信息不足以判断服务崩溃的根本原因。",
  "possible_causes": [],
  "diagnostic_steps": [],
  "suggested_fixes": [],
  "risk_notes": [],
  "citations": [],
  "answerable": false,
  "confidence": "low",
  "clarifying_questions": [
    "服务使用的模型和推理框架版本是什么？",
    "崩溃前后的错误日志是什么？",
    "当时CPU、内存和GPU显存占用是多少？",
    "近期是否修改了镜像、模型或启动参数？"
  ]
}
```

## 13. 评测需求

### 13.1 评测集规模

首版建立50～100题人工标注评测集，至少包括：

- 直接事实题；
- 故障排查题；
- 包含明确错误码的问题；
- 需要多个文档片段的问题；
- 信息不足问题；
- 知识库范围外问题；
- 高风险操作请求。

### 13.2 检索指标

| 指标 | 含义 | 目标 |
|---|---|---:|
| Recall@5 | 前5个结果是否包含标准证据 | ≥0.85 |
| Hit Rate@5 | 是否至少命中一个标准证据 | ≥0.85 |
| MRR@10 | 首个正确证据的平均倒数排名 | ≥0.70 |

### 13.3 生成指标

| 指标 | 说明 | 目标 |
|---|---|---:|
| 回答正确性 | 人工1～5分 | ≥4.0 |
| 回答完整性 | 必要步骤覆盖程度 | ≥80% |
| 引用支持率 | 引用是否支持对应结论 | ≥90% |
| 拒答准确率 | 不可回答题是否正确拒答 | ≥80% |

### 13.4 系统指标

| 指标 | 说明 |
|---|---|
| P50/P95延迟 | 端到端及各阶段延迟 |
| 首Token延迟 | 流式响应开始等待时间 |
| 吞吐量 | 单位时间完成请求数 |
| 错误率 | 各并发水平下失败请求比例 |
| Token用量 | 输入与输出Token数量 |
| 单请求成本 | 使用云端API时的估算费用 |
| 显存占用 | 本地模型空闲与负载下显存 |
| 冷启动时间 | 模型或服务从启动到就绪的时间 |

### 13.5 必做对照实验

1. 不同Chunk大小或分块策略；
2. BM25、向量检索与混合检索；
3. 有无Reranker；
4. 不同Top-k配置；
5. 云端API模型与本地量化模型；
6. 有无缓存；
7. 不同并发量。

## 14. 失败类型定义

为避免把所有错误都归因于“大模型效果不好”，项目统一使用以下分类：

### 14.1 数据失败

正确知识未被收集、解析错误、元数据缺失或内容版本过期。

### 14.2 分块失败

关键证据被错误截断、上下文过短或不同主题被混入同一Chunk。

### 14.3 检索失败

标准证据未进入候选Top-k。

### 14.4 排序失败

标准证据已被召回，但排序过低，未进入最终上下文。

### 14.5 生成失败

上下文中已有正确证据，但模型理解错误、遗漏关键信息或生成无依据结论。

### 14.6 引用失败

回答可能正确，但引用不支持相应结论，或引用指向了错误文档。

### 14.7 拒答失败

应该拒答时给出确定答案，或证据充分时错误拒答。

### 14.8 服务失败

请求因超时、依赖不可用、资源不足、非法响应或代码异常而失败。

## 15. API错误分类要求

系统应至少区分：

| 错误类型 | 示例 |
|---|---|
| `VALIDATION_ERROR` | 查询为空或输入过长 |
| `RETRIEVAL_UNAVAILABLE` | Qdrant连接失败 |
| `RERANKER_UNAVAILABLE` | Reranker加载失败 |
| `MODEL_TIMEOUT` | 生成模型调用超时 |
| `MODEL_RATE_LIMITED` | 外部API限流 |
| `MODEL_INVALID_RESPONSE` | 模型输出无法解析 |
| `INSUFFICIENT_EVIDENCE` | 证据不足，不属于系统异常 |
| `INTERNAL_ERROR` | 未预期的内部错误 |

错误响应不得暴露密钥、内部堆栈或服务器敏感路径。

## 16. 部署需求

### 16.1 开发与运行模式

- 本地Windows环境负责编码、单元测试和轻量调试；
- Linux GPU服务器负责Embedding、Reranker、本地大模型和压测；
- 代码通过Git同步，不手工维护多份副本；
- 密钥、模型权重、缓存、日志和向量库数据不通过Git同步；
- Docker用于减少本地和服务器之间的环境差异。

### 16.2 Python与依赖

- 基础Python版本建议为3.11；
- 基础API依赖和GPU依赖应合理分离；
- 服务器上的GPU框架版本必须与驱动和推理框架要求匹配；
- 项目必须记录实际使用的Python、驱动、CUDA、PyTorch和推理框架版本。

### 16.3 持久化

以下内容必须在容器重启后保留：

- Qdrant向量数据；
- 原始或处理后的知识库数据；
- 评测结果；
- 必要运行日志；
- 用户反馈数据。

### 16.4 健康检查

- 存活检查只判断应用进程能否响应；
- 就绪检查必须判断关键依赖和模型是否可以服务；
- 模型尚未加载完成时，就绪检查不得返回成功；
- 依赖恢复后，服务应能够重新进入就绪状态。

## 20. 术语说明

| 术语 | 说明 |
|---|---|
| RAG | 检索增强生成，先检索证据再生成回答 |
| Chunk | 文档经过切分得到的检索单元 |
| Embedding | 将文本映射为向量表示 |
| BM25 | 基于关键词匹配的经典检索算法 |
| Dense Retrieval | 基于Embedding相似度的语义检索 |
| Hybrid Retrieval | 融合关键词与向量检索的方法 |
| Reranker | 对候选文档进行更精确重排序的模型 |
| Recall@k | 前k个结果召回标准证据的比例 |
| MRR | 衡量首个正确结果排序位置的指标 |
| P95延迟 | 95%的请求能够在该时间以内完成 |
| 首Token延迟 | 从请求发出到收到第一个生成Token的时间 |
| 拒答 | 在证据不足或问题越界时不生成确定答案 |
| ADR | Architecture Decision Record，工程决策记录 |
